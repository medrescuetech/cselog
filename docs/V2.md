# HWRT V2 — High Risk Work Tracker

**Target version:** 2.0.0  
**Branch:** `v2/hwrt`  
**Product name:** **HWRT — High Risk Work Tracker**

This document is the authoritative V2 scope and implementation/deployment plan. V2 evolves the
original Confined Space Entry Monitor into a configurable high-risk-work tracking system while
retaining the proven live board, map, location catalogue, audit trail and cPanel deployment model.

---

## 1. V2 goals

HWRT must:

1. Track multiple categories of high-risk work, not just confined-space entry.
2. Give every high-risk-work record a permanent, human-readable unique ID.
3. Keep an easy live **Open Board** with explicit column headers.
4. Keep a short-term **Logbook** showing recent work and current/closed status.
5. Produce filtered **Reports** by date range, work type, status or all work, with CSV export.
6. Allow an Admin to configure work types, users, appearance and map information under one
   **Settings** menu.
7. Allow users to sign in using a **username**; an email address is not the identity.
8. Support a light and dark colour scheme.
9. Show the running HWRT version in the bottom-left of every authenticated screen.
10. Keep the map/data private at runtime: no ArcGIS, analytics, telemetry or third-party API is
    required to operate HWRT.
11. Be safely updateable from Git with database migrations and rollback/backup considerations.

## 3. Users, login and permissions

### V2 roles

V2 simplifies application access to two roles:

| Role | Capability |
|---|---|
| User | Open Board, Map, Log Work, close work, Logbook, Reports |
| Admin | Everything a User can do plus Settings, users, work types, map/settings and diagnostics |

Legacy `viewer`, `logger` and `supervisor` records are migrated to `user`. Existing
`admin` records remain `admin`.

### Usernames

Each account has a unique `username`.

Login accepts either:

- username; or
- email, when an email is present.

Email is optional for authentication and must not be used as the primary key or display identity.

Admin user management belongs under:

`Settings → Users`

Admin can:

- create users;
- set username/display name;
- optionally record email;
- set User/Admin role;
- activate/deactivate;
- reset password.

Safeguards:

- the signed-in Admin cannot deactivate or demote their own account;
- at least one active Admin must remain;
- passwords are hashed by Laravel and never displayed or logged.

## 4. High-risk-work types

Work types are database-driven and configurable from:

`Settings → High Risk Work Types`

Each type has:

- name;
- colour;
- display order;
- active/inactive;
- default/not default;
- notes required yes/no;
- optional notes prompt/help text;
- whether it is the special **Other** type.

Initial defaults can include:

- Confined Space Entry
- Hot Work
- Working at Heights
- Excavation
- Electrical Isolation
- Inspection
- Other

This is not a fixed regulatory list. The Admin can add, rename, reorder, retire and reactivate types
without a code deployment.

### Other

Exactly one type may be flagged as the **Other** type.

When Other is selected, the user must provide a short description of the work type. This value is
stored on the individual HRW record and remains unchanged even if work-type settings later change.

### Notes

Every HRW record has a free-text Notes field.

A work type may additionally:

- require Notes;
- define a notes prompt/placeholder, for example:
  `Crew / gas test / standby arrangements`.

The note belongs to the HRW record, not to the work-type master record.

## 5. Unique HRW identifier

Every record receives an immutable, unique human-readable identifier.

Format:

`HRW-000001`

The numeric portion is based on the database record ID and is zero padded for display.

Rules:

- generated automatically;
- unique;
- never reused;
- remains attached to the record after close/cancel;
- included on Open Board, Logbook, History, Reports and CSV exports.

Existing records are backfilled during the V2 migration.

## 6. Operational screens

### Open Board

The Open Board remains the live operational screen.

Required columns:

- HRW ID
- Elapsed
- Type
- Location
- Area
- Permit
- Notes / Reported by
- Opened
- Opened by
- Action

The existing age highlighting and close action remain.

### Log Work

The log form captures:

- HRW type;
- Other description when applicable;
- location;
- Notes;
- permit number;
- reported by;
- opened time;
- late-entry reason when applicable.

The HRW ID is generated after submission and shown on the resulting record/board.

### Logbook

A new Logbook is a simple recent-activity view intended for operational review rather than detailed
historical analysis.

Default: last 7 days.

Selectable windows:

- 3 days
- 7 days
- 14 days
- 30 days

Columns:

- HRW ID
- opened
- closed
- status
- type
- location
- area
- permit
- logged by

Open records remain visually obvious.

### Reports

A dedicated Reports screen supports:

- From date
- To date
- HRW type
- Status (open/closed/cancelled/all)
- Area, when useful
- Free-text search
- All records when filters are blank

Output includes summary totals and a detailed result table.

CSV export uses the same filters and includes HRW ID.

A later minor version may add PDF/print-formatted reports if required.

## 8. Map architecture, updating and privacy

### Runtime operation

**HWRT does not require ArcGIS at runtime.**

The browser requests local application endpoints and local static files:

- `/api/layers`
- `/api/areas`
- `/api/landmarks`
- `/sitemap/...`

The map controller reads `sitemap/manifest.json` from local disk and converts the file names into
local `/sitemap/...` URLs.

Areas and landmarks are served from the HWRT database.

No HRW entry, pin, user, note, permit, username or location-catalogue record is sent to ArcGIS by
the application.

### ArcGIS source URLs in manifest

Some `manifest.json` layers contain an ArcGIS URL in their `source` field. This is provenance
metadata only. The runtime map does not fetch those URLs.

### Refresh helper

`sitemap/tools/fetch_arcgis.py` is an **offline/download helper**. It performs anonymous HTTP GET
requests to public ArcGIS endpoints to download imagery or features.

It does not:

- authenticate to ArcGIS;
- POST HWRT data;
- upload application data;
- read the HWRT database;
- send HRW records or user information.

Ground Disturbance Permit layers containing named individuals remain deliberately excluded.

### Preferred V2 map update workflow

Map updates should be deliberate and version controlled:

1. Refresh/download source imagery/features on a dev machine or controlled build environment.
2. Rebuild `sitemap/manifest.json`.
3. Visually verify alignment using the browser acceptance tests.
4. Commit the changed `sitemap/` files to a feature branch.
5. Merge after review.
6. Update the cPanel application using the normal Git update process.
7. Run `php artisan sitemap:import`.
8. Verify Map and `/error`.

This gives a complete map-change history in Git and means production never needs direct ArcGIS
access.

### Runtime external network policy

V2 production target: **no runtime third-party network dependencies**.

The current V1-style frontend uses CDN copies of Tailwind, Alpine and Leaflet. Those CDN requests do
not contain the HWRT database, but they expose ordinary HTTP request metadata such as client IP,
browser/user-agent and potentially a referrer.

Before V2 production release, these libraries are to be served locally from HWRT so normal
operation can be fully self-contained.

No analytics or telemetry is to be added unless explicitly approved.

## 9. Database

HWRT is already database-backed.

Core data includes:

- users;
- settings;
- high-risk-work types;
- locations;
- areas/landmarks;
- HRW entries;
- entry event/audit records;
- sessions/cache/queue tables.

### Development/review

SQLite is acceptable and convenient for the dev subdomain.

### Production recommendation

For a shared multi-user production deployment on cPanel, use the host's MariaDB/MySQL service.

Reasons:

- better concurrent writes;
- simpler cPanel backup/restore tooling;
- better long-term operational support;
- avoids SQLite file-locking becoming a bottleneck.

The Laravel models and migrations remain database-portable.

V2 does not require spatial DB extensions; map geometry remains ordinary JSON/GeoJSON.

## 10. Audit and privacy

Each HRW record retains:

- created/opened time;
- created/opened by;
- closed time/by;
- close note;
- immutable HRW ID;
- location snapshot and coordinates;
- work-type relationship;
- event history.

Error logging must not log passwords or request bodies.

Application diagnostics are stored locally in:

`storage/logs/hwrt-errors.log`

Access to diagnostics is Admin-only.

## 11. Git-based update model

The production working copy keeps its environment and live database outside version control.

Never overwrite:

- `.env`
- `storage/`
- live database contents
- user-generated backups

### Routine update

Typical update:

```bash
cd ~/csem-review
git fetch --tags origin
git checkout main
git pull --ff-only origin main
composer install --no-dev --optimize-autoloader --no-interaction
php artisan migrate --force
php artisan sitemap:import
php artisan optimize
```

V2 provides an update helper to wrap these steps with a database backup and maintenance mode.

### Release update

For a fixed release:

```bash
git fetch --tags origin
git checkout v2.0.1
./scripts/update-hwrt.sh --no-git
```

### Rollback

Code rollback is a Git checkout/tag operation.

Database rollback is not assumed to be automatically safe after a migration. Before every update,
take a database backup. If a release migration is not backwards compatible, restore the backup as
part of rollback.

## 13. Additional V2 considerations

Items worth preserving or adding while doing this work:

- **Do not hard-delete work types or locations referenced by historical HRW records.**
- Keep exact coordinate snapshots on HRW entries even when catalogue locations are later moved.
- Retain the separate error/diagnostic page.
- Add database backup before Git-driven updates.
- Consider a printable shift handover report in V2.1.
- Consider a separate map-package version/date in addition to the application version.
- Consider a read-only wallboard account/mode later if it is operationally useful; V2's requested
  permission model remains User/Admin.
- Consider retention/archive rules once the required regulatory/contractual retention period is
  confirmed.
- Map refreshes should remain explicit changes, not an automatic production task.

## 14. V2 definition of done

V2.0.0 is ready for production review when:

- UI is branded HWRT;
- version is visible;
- username authentication works;
- only User/Admin roles remain;
- Settings contains Users, Work Types, Appearance and Map information;
- work-type list is configurable;
- Other works correctly;
- every HRW has an immutable unique ID;
- Notes work for every HRW and can be required/prompted by type;
- Board has headers and HRW IDs;
- recent Logbook works;
- Reports filter by date/type/status/all and export CSV;
- map remains local at runtime;
- runtime third-party CDN dependencies are removed;
- Git update process is tested on the dev cPanel instance;
- automated tests and visual map acceptance pass.
