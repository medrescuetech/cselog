# HWRT V2 — High Risk Work Tracker

**Target version:** 2.0.0  
**Branch:** `v2/hwrt`  
**Product name:** **HWRT — High Risk Work Tracker**

This document is the authoritative V2 scope and implementation/deployment plan. V2 evolves the
original Confined Space Entry Monitor into a configurable high-risk-work tracking system while
retaining the proven live board, map, location catalogue, audit trail and cPanel deployment model.

---

## 1. V2 goals

HWRT must:

1. Track multiple categories of high-risk work, not just confined-space entry.
2. Give every high-risk-work record a permanent, human-readable unique ID.
3. Keep an easy live **Open Board** with explicit column headers.
4. Keep a short-term **Logbook** showing recent work and current/closed status.
5. Produce filtered **Reports** by date range, work type, status or all work, with CSV export.
6. Allow an Admin to configure work types, users, appearance and map information under one
   **Settings** menu.
7. Allow users to sign in using a **username**; an email address is not the identity.
8. Support a light and dark colour scheme.
9. Show the running HWRT version in the bottom-left of every authenticated screen.
10. Keep the map/data private at runtime: no ArcGIS, analytics, telemetry or third-party API is
    required to operate HWRT.
11. Be safely updateable from Git with database migrations and rollback/backup considerations.

## 3. Users, login and permissions

### V2 roles

V2 simplifies application access to two roles:

| Role | Capability |
|---|---|
| User | Open Board, Map, Log Work, close work, Logbook, Reports |
| Admin | Everything a User can do plus Settings, users, work types, map/settings and diagnostics |

Legacy `viewer`, `logger` and `supervisor` records are migrated to `user`. Existing
`admin` records remain `admin`.

### Usernames

Each account has a unique `username`.

Login accepts either:

- username; or
- email, when an email is present.

Email is optional for authentication and must not be used as the primary key or display identity.

Admin user management belongs under:

`Settings → Users`

Admin can:

- create users;
- set username/display name;
- optionally record email;
- set User/Admin role;
- activate/deactivate;
- reset password.

Safeguards:

- the signed-in Admin cannot deactivate or demote their own account;
- at least one active Admin must remain;
- active Admin rows are locked during account changes so concurrent updates cannot remove the final Admin;
- passwords are hashed by Laravel and never displayed or logged.

The database seeder provisions a separate bootstrap account only when its username is unused. By
default it is `admin` / `admin`; existing Admin accounts are never modified. Set `HWRT_ADMIN_NAME`,
`HWRT_ADMIN_USERNAME`, `HWRT_ADMIN_EMAIL` and `HWRT_ADMIN_PASSWORD` in `.env` to override the
bootstrap credentials. Bootstrap and Admin-reset passwords must be changed before ordinary app
access. Rotate the setup password immediately after first sign-in.
`scripts/update-hwrt.sh` also runs `php artisan hwrt:bootstrap-admin` after migrations so existing
review databases receive the bootstrap account without re-running the seeder. If the configured
username already exists as an Admin, it and its password are left unchanged.
To reserve the default `admin` username when an older account already owns it, the migration
renames that legacy username to `legacy-admin-<id>` without changing its ID, role, email or password;
existing users can continue signing in by email when one is recorded.

## 4. High-risk-work types

Work types are database-driven and configurable from:

`Settings → High Risk Work Types`

Each type has:

- name;
- colour;
- display order;
- active/inactive;
- default/not default;
- notes required yes/no;
- optional notes prompt/help text;
- whether it is the special **Other** type.

Initial defaults can include:

- Confined Space Entry
- Hot Work
- Working at Heights
- Excavation
- Electrical Isolation
- Inspection
- Other

This is not a fixed regulatory list. The Admin can add, rename, reorder, retire and reactivate types
without a code deployment.

### Other

Exactly one type may be flagged as the **Other** type.

When Other is selected, the user must provide a short description of the work type. This value is
stored on the individual HRW record and remains unchanged even if work-type settings later change.

### Notes

Every HRW record has a free-text Notes field.

A work type may additionally:

- require Notes;
- define a notes prompt/placeholder, for example:
  `Crew / gas test / standby arrangements`.

The note belongs to the HRW record, not to the work-type master record.

## 5. Unique HRW identifier

Every record receives an immutable, unique human-readable identifier.

Format:

`HRW-000001`

The numeric portion is based on the database record ID and is zero padded for display.

Rules:

- generated automatically;
- unique;
- never reused;
- remains attached to the record after close/cancel;
- included on Open Board, Logbook, History, Reports and CSV exports.

Existing records are backfilled during the V2 migration.

## 8. Map architecture, updating and privacy

### Runtime operation

**HWRT does not require ArcGIS at runtime.**

The browser requests local application endpoints and local static files:

- `/api/layers`
- `/api/areas`
- `/api/landmarks`
- `/sitemap/...`

The map controller reads `sitemap/manifest.json` from local disk and converts the file names into
local `/sitemap/...` URLs.

Areas and landmarks are served from the HWRT database.

No HRW entry, pin, user, note, permit, username or location-catalogue record is sent to ArcGIS by
the application.

### ArcGIS source URLs in manifest

Some `manifest.json` layers contain an ArcGIS URL in their `source` field. This is provenance
metadata only. The runtime map does not fetch those URLs.

### Refresh helper

`sitemap/tools/fetch_arcgis.py` is an **offline/download helper**. It performs anonymous HTTP GET
requests to public ArcGIS endpoints to download imagery or features.

It does not:

- authenticate to ArcGIS;
- POST HWRT data;
- upload application data;
- read the HWRT database;
- send HRW records or user information.

Ground Disturbance Permit layers containing named individuals remain deliberately excluded.

### Preferred V2 map update workflow

Map updates should be deliberate and version controlled:

1. Refresh/download source imagery/features on a dev machine or controlled build environment.
2. Rebuild `sitemap/manifest.json`.
3. Visually verify alignment using the browser acceptance tests.
4. Commit the changed `sitemap/` files to a feature branch.
5. Merge after review.
6. Update the cPanel application using the normal Git update process.
7. Run `php artisan sitemap:import`.
8. Verify Map and `/error`.

This gives a complete map-change history in Git and means production never needs direct ArcGIS
access.

### Runtime external network policy

V2 production target: **no runtime third-party network dependencies**.

The V1 CDN references have been replaced by local Tailwind, Alpine and Leaflet assets. Refresh the
checked-in deployment assets with `npm ci && npm run build`; runtime operation does not contact
their upstream CDNs.

No analytics or telemetry is to be added unless explicitly approved.

## 9. Database

HWRT is already database-backed.

Core data includes:

- users;
- settings;
- high-risk-work types;
- locations;
- areas/landmarks;
- HRW entries;
- entry event/audit records;
- sessions/cache/queue tables.

### Development/review

SQLite is acceptable and convenient for the dev subdomain.

### Production database

For a shared multi-user cPanel deployment, use the host's MySQL-compatible service rather than
SQLite. Configure `DB_CONNECTION=mysql` for MySQL or `DB_CONNECTION=mariadb` for MariaDB; both
drivers use the same application schema and migrations. CI runs the migration and feature suite
against MySQL 8.4 and MariaDB 11.4 to guard that portability.

The database engine can be changed later, but changing `DB_CONNECTION` alone does not move data.
Before switching, take and verify a logical backup, provision the target database, restore/import
the backup with a database-native dump/restore tool, set the new connection variables in `.env`,
then run `php artisan migrate:status` and application smoke tests. Keep the original database and
backup unchanged until the target is accepted. Do not run a fresh migration against an empty
target as a substitute for restoring production data.

V2 does not require spatial DB extensions; map geometry remains ordinary JSON/GeoJSON.

## 11. Git-based update model

The production working copy keeps its environment and live database outside version control.

Never overwrite:

- `.env`
- `storage/`
- live database contents
- user-generated backups

### Routine update

Typical update:

```bash
cd ~/csem-review
git fetch --tags origin
git checkout main
git pull --ff-only origin main
composer install --no-dev --optimize-autoloader --no-interaction
php artisan migrate --force
php artisan sitemap:import
php artisan optimize
```

V2 provides an update helper to wrap these steps with a database backup and maintenance mode.

The additive V2 hardening migration adds `must_change_password` and changes the database default
role to `user`, preventing new records from inheriting the V1 `logger` role. V1 role conversion is
not reversible; restore the pre-update database backup for a database rollback.

### Release update

For a fixed release:

```bash
git fetch --tags origin
git checkout v2.0.1
./scripts/update-hwrt.sh --no-git
```

### Rollback

Code rollback is a Git checkout/tag operation.

Database rollback is not assumed to be automatically safe after a migration. Before every update,
take a database backup. If a release migration is not backwards compatible, restore the backup as
part of rollback.

## 15. V2 scope additions — scheduling, Perth time, location PDFs, landmarks and live map refresh

These items are part of V2.0.0 and supersede any earlier wording in this document where there is a conflict.

### Australia/Perth time source

Operational dates/times use Laravel's `APP_TIMEZONE=Australia/Perth`.

- Immediate starts use the server-side Perth time.
- Late-entry timestamps entered through `datetime-local` are interpreted as Perth time.
- Planned starts are interpreted as Perth time.
- Board date boundaries for “today” are Perth calendar boundaries, regardless of browser timezone or cPanel server timezone.
- The log screen displays a Perth clock.

### Advance scheduling / Pending

A job can be logged before work starts by supplying a future planned start.

- It receives its permanent `HRW-xxxxxx` ID immediately.
- Status is `pending`.
- `planned_start_at` preserves the planned Perth start.
- `scheduled_by` records who scheduled it.
- All pending records appear under **Pending**.
- Pending records whose planned date is today in Perth appear under **Pending Today** on the Open Board.
- Pending work does not silently become Open.
- A user presses **Start** when work actually begins; HWRT then records the actual start time and starter.
- Pending work can be cancelled with an audit event.

### Optional PDF per catalogue location

A catalogue location can have one optional PDF.

- Upload/replace/remove is Admin-only under **Settings → Locations & PDFs**.
- Files are stored in Laravel private storage, not the public web root.
- Authenticated users download them through a protected route.
- When an open HRW uses that catalogue location, its map pin popup includes an **Open location PDF** link.
- Replacing a PDF removes the previous stored file.

### Manual key landmarks

Admins can manage key landmarks under **Settings → Landmarks**.

- name;
- category;
- active/inactive;
- MGA Zone 50 easting/northing.

The creation screen includes the live local map. Clicking the map fills the easting/northing fields so a landmark can be added without calculating coordinates separately.

Imported ArcGIS landmarks and manually entered landmarks coexist in the same local database.

### Automatic/manual map refresh

The operational map continues to serve local files only.

Settings offers:

- Manual only
- Daily
- Weekly
- Monthly
- Request refresh now

The refresh job:

1. discovers the current public imagery service, or uses an Admin override;
2. reads the installed Site C/F L17 sidecar;
3. uses that exact current Site C/F extent as the refresh bounding box;
4. downloads replacement L17/L16 imagery and the existing feature datasets to a staging directory;
5. validates that required staged files exist and are non-empty;
6. replaces runtime map files only after the full download phase succeeds;
7. rebuilds the local manifest;
8. re-runs `sitemap:import`;
9. records last attempt, last success, status and error.

The existing engineering-plan overlays remain unchanged by routine automatic refresh. A plan-overlay change remains a reviewed Git change.

No HRW job, user, note, permit, PDF or database content is included in the ArcGIS requests.

### Runtime map copy and Git updates

Production/review should store versioned packages under `storage/app/hwrt-sitemap/versions/`,
with `storage/app/hwrt-sitemap/current` as a symlink to the active package and:

`public/sitemap -> ../storage/app/hwrt-sitemap/current`

`HWRT_SITEMAP_PATH` points to the `current` symlink. Refresh builds and validates a complete
replacement package beside the active package, imports its GeoJSON in a database transaction, and
then atomically switches the pointer. If import fails, the previous pointer is restored. The
previous package is retained for rollback, and the importer validates every required source before
mutating its database tables.

This is deliberately separate from the Git-tracked seed package at `sitemap/`. Automatic map refresh therefore does not dirty the Git working tree or interfere with later `git pull` / release updates.

`scripts/update-hwrt.sh` seeds or migrates the runtime map when needed, backs up SQLite when
present, performs the Git/Composer/migration/update sequence and re-imports the current package.

### Revised V2.0.0 acceptance criteria

In addition to the criteria above, V2.0.0 requires:

- Pending scheduling works in Australia/Perth time.
- Pending Today appears on the Board for the correct Perth date.
- Start preserves the planned time and records actual commencement.
- Location PDFs remain private and are reachable from map pin details.
- Manual landmarks can be added from a map click.
- Map refresh can be manual or scheduled while retaining the existing map footprint.
- Runtime map refresh does not modify Git-tracked map files.
